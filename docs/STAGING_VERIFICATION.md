## Remaining acceptance and limits

- Recheck the actual Azure Linux VM: TLS certificate/renewal and HTTPS redirect, browser Secure-cookie transport, exact public origins, host-edge source CIDR, spoofed forwarding headers, distinct-client rate limiting, and blocked direct DB/API/frontend access. Local HTTP uses explicit test overrides. The separate production API probe verifies configuration/cookie attributes, not encrypted transport.
- Rehearse migration-owner adoption and upgrades against a backup of the actual existing database before changing its credentials. The synthetic initial-schema upgrade proves this additive migration preserves its fixture; it does not certify every historical deployment or future incompatible migration.
- Repeat changed-address replacement, shutdown/drain, dependency recovery and restore on the target host and its actual proxy path. Establish off-host backup retention, restore access controls, operational monitoring, recovery objectives and capacity measurements.
- Browser coverage is Chromium desktop/mobile viewport, not Safari/Firefox or full accessibility verification. No load benchmark, penetration test, container/OS vulnerability scan, host-loss recovery or multi-host failover certification was performed.
- Academic rules remain a planning heuristic. Real advising still requires authoritative admission-year-specific university review; metadata and URLs alone do not confer official status.

These results support a staging release rehearsal. They do **not** establish public-production readiness. Follow [STAGING.md](STAGING.md) for the configuration, existing-data procedure and release compatibility review.
