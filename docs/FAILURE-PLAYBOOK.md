# UniPath failure playbook

The observed cases below come from the [manual Azure deployment](CLOUD-LEARNING.md) and [Terraform deployment](TERRAFORM-AZURE-LAB.md). The practice cases are hypothetical. In an interview, describe what you personally ran, what the project record shows, and what you would test next.

## Project 1 — Manual Azure VM deployment

| Observed symptom                                                                                           | Diagnosis, response, and evidence                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Azure rejected a VM size in UAE North with `NotAvailableForSubscription`.                                  | Region permissions, family quota, and SKU availability are separate checks. The working deployment used Denmark East after checking the subscription's options.                        |
| GitHub rejected HTTPS cloning with an account password.                                                    | The VM needed its own repository credential. A read-only deploy key scoped to UniPath allowed cloning. That key was separate from the key used to log into the VM.                     |
| WSL SSH rejected a private key stored in Windows Downloads.                                                | OpenSSH reported overly broad permissions. Moving the key into WSL's Linux home and setting the directory to `700` and key to `600` resolved it. This was a local key-file problem.    |
| GitHub Actions failed on a Docker test that reserved a fixed container IP, then on `compose start --wait`. | The disposable network needed an explicit subnet. The runner's Compose version also rejected that command form. The test used `up -d --no-deps --wait`, and both CI jobs later passed. |
| The API process stayed alive when PostgreSQL stopped.                                                      | This was a deliberate outage exercise. Liveness stayed responsive while readiness returned 503. Restarting PostgreSQL restored readiness without restarting the API.                   |

**Interview prompt — How did you prove the database was recoverable?** The project restored a custom-format dump into a separate database, matched counts for four tables, and compared SHA-256 hashes after copying the dump off the VM. That exercise verified a logical restore. The full application recovery was tested in project two.

### Project 1 practice cases

| Scenario                                                                | How to diagnose and recover                                                                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The browser cannot open the SSH tunnel endpoint.                        | First run `curl -i http://127.0.0.1:8080/health/ready` on the VM. If it passes, check the local forwarding command and whether port 8080 is already occupied locally. If the VM-side request fails, inspect `sudo docker compose ps -a` and the service logs.                                                                     |
| The API returns 502 through Nginx after the API container was replaced. | Compare the API's health inside its container with readiness through Nginx. Check both services' logs and verify Docker DNS resolves the backend service name. A stale upstream address is one possible cause. Reproduce it by replacing the backend in a disposable stack and checking the proxied endpoint.                     |
| UniPath starts with an empty database after a cleanup command.          | Check the Compose project name and mounted volume. `docker compose down -v` can remove the project's named data volume. Restore a verified dump into a fresh database and confirm records and readiness. Rehearse using a throwaway stack. [Docker Compose reference](https://docs.docker.com/reference/cli/docker/compose/down/) |

## Project 2 — Terraform deployment and rebuild

| Observed symptom                                                              | Diagnosis, response, and evidence                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The VM was running, but SSH timed out.                                        | The NSG allowed the workstation's private LAN address. Updating the Terraform input to the internet-facing IPv4 address with a `/32` prefix restored SSH. A timeout points toward the connection path; `Permission denied (publickey)` means the SSH server was reached.                                              |
| Azure CLI returned a generic `Bad Request` when assigning the blob data role. | The visible IDs looked valid. In WSL, `printf '%q\n'` can reveal invisible carriage returns in CLI output. The troubleshooting steps stripped carriage returns and retried. The role assignment and private container creation subsequently succeeded; the original error did not identify a definitive cause.        |
| The VM's tag differed from the Terraform code.                                | This was intentional drift. Changing the tag in Azure produced a one-resource update plan. Applying restored the declared value, and the next plan was clean.                                                                                                                                                         |
| Native auto-shutdown could not be created.                                    | Azure did not offer the schedule resource in Denmark East. The subscription's region policy rejected North Europe. The project used a scoped monthly budget with email alerts and verified manual deallocation instead.                                                                                               |
| The first off-VM backup transfer produced no checksum.                        | The transfer was retried using a positional argument format that Azure Run Command accepted. The private blob bundle downloaded successfully, its hash matched the VM copy, and a local copy was verified before teardown. The replacement VM restored the dump and returned HTTP 200 for the homepage and readiness. |

**Interview prompt — What if Terraform state survived but the VM disk didn’t?** State identifies the infrastructure Terraform manages. It does not contain PostgreSQL records. The project kept remote state in a separate resource group and the database dump off the VM. Terraform recreated all nine resources, then the application and database were restored separately. PostgreSQL reported one user and one saved plan, and the final infrastructure plan showed no changes.

### Project 2 practice cases

| Scenario                                                                 | How to diagnose and recover                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `terraform init` returns 403 against Blob Storage.                       | Check the signed-in Azure identity, account and container, then try listing blobs using `--auth-mode login`. If that fails, distinguish a missing blob data role or propagation delay from a network restriction. Management permissions and blob data permissions are separate.                                                                                      |
| The backend reports a state lock after a terminal crash.                 | Read the lock details and check whether another run still owns it. Wait for active operations. Use `force-unlock` only for your own confirmed stale lock. Re-run the plan after clearing it. [Terraform state locking](https://developer.hashicorp.com/terraform/language/state/locking)                                                                              |
| Terraform proposes nine additions while the lab still exists in Azure.   | Stop before applying. Check the backend account, container, blob key, workspace, and `terraform state list`. Reconnect to the correct state first. If state is genuinely lost, recover a known-good backup or import existing resources deliberately and review the resulting plan. [Terraform import](https://developer.hashicorp.com/terraform/cli/commands/import) |
| A rebuild succeeds, but the old SSH address or host key no longer works. | Read the new IP from Terraform and confirm it against Azure. For a host-key mismatch, verify the new host fingerprint through Azure management access before replacing the old known-host entry. Then check the NSG and reconnect.                                                                                                                                    |
