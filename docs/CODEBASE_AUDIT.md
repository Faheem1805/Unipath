# UniPath codebase audit

> **Historical audit snapshot.** The observations and failures below describe the pre-fix code on 22 October 2026. The repository is now initialized and connected to GitHub. Follow-up changes and newly executed regression/acceptance results are tracked separately in [STAGING_VERIFICATION.md](STAGING_VERIFICATION.md); the original 40 passing tests do not close these findings. Deployment configuration and target-VM requirements are in [STAGING.md](STAGING.md).

**Audit date:** 22 October 2026  
**Purpose:** Assess the existing application as a foundation for Azure Cloud Engineering exercises. This is an audit, not a redesign or deployment approval.

## Verdict

UniPath has a real, working application foundation: authenticated accounts, PostgreSQL persistence, academic rules, administrative imports, migrations, and meaningful automated tests. The fresh baseline checks passed **19 unit tests, 15 API integration tests, and 6 browser tests: 40 tests total**. Two separate backend processes accepted the same database-backed session, and saved records survived an API restart.

**Do not treat those results as public deployment sign-off.** Additional probes confirmed a password-change/login race, an empty-catalog administrator bootstrap failure, academic edge cases, and an administrator editor crash. Production settings and database privileges also need attention. A follow-up after Docker/WSL became available successfully built and started the Linux stack, repeated all 40 tests, verified persistence and rehearsed database restoration. It also confirmed a stale Nginx upstream after a backend address change and forced termination of a blocked request. TLS and the actual Azure VM remain untested.

The three highest priorities before an Azure Linux VM deployment are:

1. Fix the authentication race and add a deterministic regression test.
2. Prepare an explicit production configuration, including HTTPS/secure cookies and a least-privilege runtime database account.
3. Fix operational replacement/shutdown behavior: Nginx must follow a changed backend address, and container stop timing must allow application requests to drain. Recheck these on the target Linux VM. Resolve the administration bootstrap problem if deploying without demo data.

No Azure resources, Terraform, load balancing, autoscaling, or other cloud infrastructure were created. No application source or deployment configuration was changed for this audit. This report is the only intended repository deliverable; temporary diagnostic helpers, copied build outputs, and logs are under ignored `.local/audit-20261022/` and `.local/docker-audit/`.

## Prioritized findings

Priority definitions: **P1** should be resolved before the relevant public/production use; **P2** is important correctness or operational work; **P3** is maintenance. No P0 issue or embedded production credential was identified within the inspected snapshot. This is not a formal penetration test.

### A-01 — P1: Concurrent login can defeat password-change session revocation

**Evidence:** [`backend/src/app.ts`](../backend/src/app.ts), login around lines 202–217 and password change around lines 233–259; session model in [`database/schema.prisma`](../database/schema.prisma).

Login reads a user's password hash and later creates a session after asynchronous password verification. Password change updates the hash and deletes existing sessions in a transaction, but does not serialize against an already-started login. That login can subsequently create a fresh session based on the old hash.

The controlled probe paused a real Prisma user lookup after its database read, changed the password through the real HTTP API, then resumed the pending login. Both requests returned 200, and the cookie issued using the old password authenticated against the primary API after the password change. This requires a precisely overlapping login; it does not mean all old-password logins work after a change.

**Fix:** Serialize credential validation/session creation with password changes, or introduce an authentication version with atomic issuance and validation semantics. Add a deterministic concurrency regression test proving that an old-credential login cannot leave a valid post-change session. Sequential logout/password tests are insufficient.

### A-02 — P1: Production configuration and runtime database privileges need separation

**Evidence:** [`docker-compose.yml`](../docker-compose.yml), [`backend/src/config.ts`](../backend/src/config.ts), [`scripts/init-env.mjs`](../scripts/init-env.mjs).

Compose defaults to `NODE_ENV=development`, insecure cookies and a loopback HTTP origin. The current local environment also uses development settings. The frontend publishes port 8080 without a host-address restriction. Leaving these settings unchanged either exposes development behavior or makes legitimate public-origin mutations fail origin validation. The production guard correctly rejects insecure cookies/non-HTTPS origins when production mode is explicitly selected.

The runtime API also uses the same PostgreSQL bootstrap credentials as the database and migration job. The local role was confirmed to have `rolsuper`, `rolcreatedb` and `rolcreaterole`. A compromised API should not have cluster-owner capabilities.

**Fix:** Define and validate explicit production values: production mode, exact public HTTPS origins, secure cookies, private random credentials, and a proxy trust boundary matching the actual request path. Use a separate least-privilege application role and a migration owner. Do not expose database/backend ports publicly. The audit found no need to implement Azure resources to establish these application deployment requirements.

### A-03 — Linux Compose startup gate passed; target-host acceptance remains

**Evidence:** [`docker/backend.Dockerfile`](../docker/backend.Dockerfile), [`docker/frontend.Dockerfile`](../docker/frontend.Dockerfile), [`docker/nginx.conf.template`](../docker/nginx.conf.template), [`docker-compose.yml`](../docker-compose.yml).

Follow-up runtime evidence now confirms Linux builds, Prisma native-engine operation, Nginx startup, Compose dependencies/health, non-root API execution, and database persistence/restoration. The original Windows production-dependency approximation is no longer the only packaging evidence. The test stack used HTTP/development settings on Docker Desktop/WSL2; it did not exercise the real Azure VM or its TLS path.

**Remaining acceptance:** Fix A-10/A-12, then repeat lifecycle tests on the intended Linux VM with the actual HTTPS/proxy settings. Verify off-host backup storage and restore onto a separate host/cluster before relying on disaster recovery. A named volume is persistence, not a backup. The local same-cluster restore rehearsal passed, but does not cover loss of the host or volume.

### A-04 — P1 when `SEED_DEMO=false`: Fresh administrator cannot reach the import UI

**Evidence:** [`frontend/src/components/layout.tsx`](../frontend/src/components/layout.tsx), profile gate at lines 62–63; [`backend/src/create-admin.ts`](../backend/src/create-admin.ts); [`backend/src/seed.ts`](../backend/src/seed.ts).

The administrator creation command creates an account without a student profile. The authenticated application layout requires every account to finish curriculum onboarding before accessing `/app/admin`. With no published curriculum, onboarding cannot continue. A fresh no-demo database reproduced that redirect and disabled button.

**Fix:** Allow authorized administration independently of student onboarding, or provide a supported explicit initial-catalog bootstrap. Authenticated administrator APIs remain a possible manual workaround; the entire database is not unrecoverable. Demo-seeded deployments do not hit this exact bootstrap condition.

### A-05 — P2: Future sequencing imposes unused OR-corequisite branches

**Evidence:** [`shared/src/engine.ts`](../shared/src/engine.ts), `addCorequisites` around lines 188–204.

The sequence helper recursively adds every corequisite under both `all` and `any`, even when another OR branch is already satisfied. In the probe, A required concurrent B **or** completed C; B required prior completion of A; C was completed. A was correctly eligible, and A then B was feasible. Projection instead produced no semester and 6 unresolved credits because it unnecessarily bundled B with A.

**Fix:** Select a satisfied/feasible OR branch before expanding concurrent groups. Add this fixture to academic regression coverage. Do not present the current projection as a guaranteed graduation schedule.

### A-06 — P2: Map and planner disagree about corequisite term context

**Evidence:** [`shared/src/engine.ts`](../shared/src/engine.ts), in-progress set around lines 81–100; [`frontend/src/pages/planner.tsx`](../frontend/src/pages/planner.tsx); [`backend/src/app.ts`](../backend/src/app.ts), plan eligibility around lines 393–410.

The progress/map calculation treats every in-progress attempt as concurrent, regardless of its stored term. The planner/API uses the selected plan codes as the concurrent set. An old-term PH101 enrollment therefore made PH102 eligible on the map, while the planner-context rule evaluation rejected PH102 alone. Conversely, an already-enrolled same-term partner is not automatically included in the selected-only planner context.

**Fix:** Define target-term enrollment and selected-course context once and reuse it in map, planner and API validation. The engine discrepancy was executed directly; the specific term fixture was not separately submitted through a browser plan-save request.

### A-07 — P2: Cycle validation rejects some feasible alternative prerequisites

**Evidence:** [`shared/src/schema.ts`](../shared/src/schema.ts), prerequisite traversal around lines 106–116.

Validation flattens prerequisite references before cycle detection. A requires B **or** C; B requires A; C has no requirements. C → A → B is feasible, but the import is rejected as cyclic because of the optional A/B branch.

**Fix:** Make validation aware of alternatives, or explicitly document this conservative restriction for importers. This does not block the present demo curriculum.

### A-08 — P2: Invalid admin document shape crashes the editor

**Evidence:** [`frontend/src/pages/admin.tsx`](../frontend/src/pages/admin.tsx), JSON parse around line 69 and course rendering around line 313.

The editor treats any parseable JSON as a typed curriculum before validating its structure. Entering `{"courses":{}}` in an editable draft invokes `.map` on an object and displays the global “Let's reconnect your path” boundary. React catches the error, so the probe's unhandled `pageerror` list was empty; the boundary was visibly present. Backend validation still protects stored documents.

**Fix:** Validate shape before derived rendering and show field-level feedback while preserving the draft text. This is a small correctness fix, not a reason to redesign administration.

### A-09 — P2: Verification labels do not establish official provenance

**Evidence:** [`shared/src/schema.ts`](../shared/src/schema.ts), verification refinement; [`frontend/src/pages/admin.tsx`](../frontend/src/pages/admin.tsx), directory defaults.

Verification requires metadata/source references, but accepts arbitrary HTTPS references and future verification dates. There is no reviewer identity field; directory editors initialize a fixed `2026-10-22` date. The audit accepted a synthetic future date with otherwise conforming source fields.

**Fix:** Keep demo and official claims distinct. Before real advising use, record review identity/time and establish an authoritative admission-year source review process. Reject future verification dates or document why they are allowed. Do not promote the fictional 124-credit dataset to official status merely by toggling a label.

### A-10 — P2: Shutdown timing and operational diagnostics need acceptance

**Evidence:** [`backend/src/server.ts`](../backend/src/server.ts), [`backend/src/app.ts`](../backend/src/app.ts), Compose and Nginx configuration.

The API allows 15 seconds before forced shutdown; Compose specifies no `stop_grace_period`. Docker documents a default of 10 seconds, so container termination can preempt the application's own drain deadline. The follow-up confirmed a failure under a deliberately blocked database request: idle stop exited 0, but active stop produced exit 137 and a 502 to the client. Docker events showed SIGTERM then SIGKILL about 3 seconds apart on this Docker Desktop/Compose installation, before the application's 15-second timeout; no explicit container stop timeout was configured. The documented default must not be mistaken for the observed grace on this host. See the [Docker Compose service reference](https://docs.docker.com/reference/compose-file/services/#stop_grace_period).

Readiness executes a database connectivity query, not a comprehensive schema-version or critical-table check. Startup checks the curriculum table, not every table. A database outage/recovery was handled, but recovery took about 17 seconds in the single local probe. Do not configure health behavior on the assumption recovery is instantaneous.

API request logging is structured, but unexpected-error events carry little diagnostic detail beyond error type and correlation. This can make migration/permission/query failures difficult to distinguish. Nginx JSON access logs were exercised and parsed successfully; its error log is conventional text.

**Fix:** Set an explicit container grace period beyond the application drain deadline and ensure request/query deadlines fit within it; rerun the controlled active-request Linux shutdown test. A hanging dependency may still require a bounded, logged failure, but should not be cut off unexpectedly by the container stop budget. Include safe, non-secret diagnostic error codes/context and establish schema rollout checks. Preserve credential/body/query redaction.

### A-11 — P3: Tooling consistency and repository hygiene

There is no lint suite, two files fail Prettier, and the root/README Node floor (`>=22.12`) is lower than the installed pnpm 11.25.0 package's engine requirement (`>=22.13`). Initial tests ran on Node 24.19.0; the follow-up also exercised Node 22.23.4 inside Linux containers. The advertised lower boundary itself was not tested. Align the documented minimum and actual pinned tooling, then add appropriate checks when setting up CI. Initialize version control and inspect exclusions before publishing this currently non-Git directory. The bundle-size advisory is lower priority than deployment correctness.

### A-12 — P1 operational: Nginx retains a replaced backend's old address

**Evidence:** [`docker/nginx.conf.template`](../docker/nginx.conf.template), static `proxy_pass http://${API_UPSTREAM}`; follow-up changed-address probe.

The template substitutes a service name when Nginx starts, and the resulting static upstream is resolved then. Ordinary backend recreation happened to reuse its address and passed. A controlled second test ensured the replacement received a different address: the new API was healthy internally (200), while requests through the still-running Nginx returned 502. Restarting Nginx immediately restored readiness and authenticated data access.

**Fix:** Provide runtime service-name resolution suitable for the actual proxy, or a reliable frontend reload/restart step when a backend address changes. Add a replacement test that guarantees a changed address; a restart reusing the same address does not cover this case. This is an application packaging/operations finding, not a request to implement a load balancer or Azure infrastructure.

## Security and secret review

Positive controls observed include salted scrypt hashing and timing-safe comparison; random 256-bit session tokens stored as hashes; HttpOnly/SameSite cookies; administrator authorization independent of client-supplied role; exact-origin checks on mutations; request-size and Zod input validation; database-backed throttling; account ownership checks; immutable published/used curriculum protection; security headers; and request correlation. Existing tests exercise unauthorized access, cross-origin mutations, role injection, invalid records, stale revisions and sequential session revocation.

The inspected source/configuration contained **no identified real hardcoded production secret**. Matches were test fixtures, documented placeholders, or local-development helper values. `.env` is present locally and excluded by both Git and Docker ignore rules; production values must be supplied separately. The local generated database password was not a placeholder, and the rate-limit secret length was 64 characters. Secret values are not reproduced in this report.

Limits: no Git history exists here to scan; zero package advisories is a registry snapshot, not proof of absence of vulnerabilities; container/OS/native-binary scanning and a formal penetration test were not performed. Scrypt cost parameters are implicit Node defaults and not versioned in stored hashes; calibration and hash-version strategy can be considered for the actual deployment capacity. The confirmed race and overprivileged DB connection deserve attention before optional authentication enhancements.
